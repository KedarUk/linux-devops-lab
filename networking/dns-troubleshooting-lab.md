# Diagnose a DNS lookup problem

**Goal:** Check whether a hostname resolves and distinguish a DNS problem from an application or network problem.

**Prerequisites:** A Linux machine with `getent`. Install the `dig` utility if it is not already available (often provided by `dnsutils` or `bind-utils`).

## 1. Check the system resolver

```bash
getent ahosts example.com
```

This uses the host's normal name-service configuration, like many applications do. One or more IP addresses means the system resolved the name. No output or an error suggests checking the resolver configuration and network.

## 2. Query DNS directly

```bash
dig example.com A
```

Read the `status` and `ANSWER SECTION`:

- `status: NOERROR` with an answer means the DNS server returned a record.
- `NXDOMAIN` means that DNS says the name does not exist.
- An empty answer can mean that no A record was returned; the name may have other record types.
- A timeout means the DNS query did not receive a response in time.

Compare IPv4 and IPv6 answers:

```bash
dig +short example.com A
dig +short example.com AAAA
```

## 3. Inspect which resolver is configured

On systems using systemd-resolved:

```bash
resolvectl status
```

Check the DNS servers and search domains for the active network link. On other distributions, inspect `/etc/resolv.conf` and the network manager configuration. Avoid overwriting resolver files by hand; they may be generated by the network manager.

## 4. Separate DNS from HTTP reachability

If the hostname resolves, test an HTTP request:

```bash
curl -I --max-time 5 https://example.com/
```

A DNS lookup can succeed while the connection still fails because of routing, firewall rules, TLS, or the remote service. Conversely, an HTTP response status confirms that the request reached an HTTP server even if the status indicates an application-level problem.

## Practice exercise

Run the commands for a hostname that works and one that does not in your lab. Record the resolver, DNS status, returned record, and HTTP result. This gives you evidence to distinguish a misspelled hostname, DNS configuration issue, and service connectivity issue.

## Key takeaway

Use `getent` to test the system's normal lookup path, `dig` to inspect DNS answers, and `curl` to test the application connection. Each checks a different layer.
